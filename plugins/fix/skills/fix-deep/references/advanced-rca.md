# 高级根因分析框架

## 概述

当标准的"向后追踪"方法不够用时，使用以下 3 种框架进行更深入的根因分析。

**使用时机：**
- 失败升级协议第 2 级（尝试 2 次修复失败后）→ 强制执行 Change Analysis + Barrier Analysis
- 偶发 bug（无法稳定复现）→ 使用 Fault Tree Analysis
- 回归 bug（以前正常，现在不正常）→ 使用 Change Analysis

## 1. Change Analysis（变更分析法）

### 适用场景

- 系统曾经正常工作，突然出问题（回归 bug）
- 升级依赖/引擎版本后出现问题
- 合并代码后出现问题
- "昨天还好好的，今天就不行了"

### 核心问题

**"上次正常和首次异常之间，什么发生了变化？"**

### 操作步骤

#### Step 1：确定时间窗口

```bash
# 查看近期提交
git log --oneline -20

# 如果知道大致时间范围
git log --oneline --after="2026-03-25" --before="2026-03-30"
```

#### Step 2：二分定位（git bisect）

```bash
git bisect start
git bisect bad HEAD                    # 当前版本有 bug
git bisect good <上次正常的commit>      # 这个版本没问题

# 对每个中间 commit：
# 1. 构建/运行项目
# 2. 测试是否复现 bug
# 3. git bisect good 或 git bisect bad

# git bisect 自动缩小范围，最终定位到引入 bug 的 commit
git bisect reset  # 结束后恢复
```

#### Step 3：分析变更

```bash
git show <定位到的commit>
# 逐行分析引入了什么变化
```

#### Step 4：扩展检查

- 同一时间段是否有**依赖更新**？（package.json / package-lock.json 变更）
- 是否有**配置变更**？（tsconfig、构建脚本、引擎版本等）
- 是否有**环境变化**？（Node 版本、操作系统、CI 环境）
- 是否有**合并冲突解决**引入的问题？

## 2. Barrier Analysis（屏障分析法）

### 适用场景

- bug 已修复，需要理解"为什么没被提前发现"
- 同类 bug 反复出现
- 想要系统性地加固防御
- Phase 5（防御加固）的分析依据

### 核心问题

**"哪些防护层本该拦住这个 bug？每层为什么没生效？"**

### 检查表

逐层评估每个屏障的状态：

| 屏障层 | 可能状态 | 评估结果 |
|--------|----------|----------|
| **TypeScript 类型系统** | 不存在 / 存在但不完善 / 存在但被 as any 绕过 / 有效 | [填写] |
| **单元测试** | 不存在 / 覆盖不足 / 场景遗漏 / 有效 | [填写] |
| **代码审查** | 未审查 / 审查未发现 / 有效 | [填写] |
| **CI 流水线** | 不存在 / 存在但未覆盖该场景 / 有效 | [填写] |
| **运行时验证** | 不存在 / 存在但逻辑错误 / 有效 | [填写] |
| **Lint / 静态分析** | 不存在 / 规则不足 / 有效 | [填写] |
| **集成测试** | 不存在 / 覆盖不足 / 有效 | [填写] |

### 输出

**修复 = 修代码 + 加固最薄弱的屏障**

找到状态为"不存在"或"存在但不完善"的屏障，在 Phase 5 中重点加固。

示例：
```
Bug: 传入了 null 导致 TypeError
屏障分析:
- TypeScript 类型：参数标注为 string 但未排除 null → 改为 string | null 或添加 NonNullable
- 单元测试：未覆盖 null 输入场景 → 添加边界测试用例
- 运行时验证：函数入口无参数检查 → 添加 Phase 5 Layer 1 验证
```

## 3. Fault Tree Analysis（故障树分析）

### 适用场景

- 偶发 bug（有时出现有时不出现）
- 多条件同时满足才触发的问题
- 时序相关的 bug（竞态条件、初始化顺序）
- 游戏引擎中的偶发崩溃
- "只在某些设备/某些操作顺序下才出现"

### 核心方法

从故障事件出发，用 **AND/OR 逻辑门**向下展开所有可能的原因组合。

### 构建步骤

#### Step 1：定义顶层故障事件

```
顶层故障：用户点击按钮后游戏卡死
```

#### Step 2：展开第一层原因（OR 门 — 任一即可触发）

```
游戏卡死 (OR):
├── 原因 A：事件处理函数抛出异常
├── 原因 B：进入死循环
├── 原因 C：主线程被阻塞操作卡住
└── 原因 D：内存溢出导致浏览器无响应
```

#### Step 3：展开子原因（AND 门 — 必须同时满足）

```
原因 A：事件处理函数抛出异常 (AND):
├── A1：回调函数中访问了已销毁的节点
└── A2：异常未被 try-catch 捕获

原因 B：进入死循环 (AND):
├── B1：while 循环的退出条件依赖外部状态
└── B2：外部状态在特定时序下未更新
```

#### Step 4：逐个验证/排除

- 对每个叶子节点添加诊断日志
- 复现问题，观察哪些条件同时满足
- 定位根因组合

### 游戏引擎常见故障树模式

```
偶发崩溃 (OR):
├── 资源加载时序 (AND):
│   ├── 异步加载未完成
│   └── 代码假设同步可用
├── 状态竞争 (AND):
│   ├── 两个组件修改同一数据
│   └── 执行顺序不确定（依赖 siblingIndex）
├── 内存问题 (AND):
│   ├── 节点销毁后仍被引用
│   └── 引用处未做 isValid 检查
└── 事件时序 (AND):
    ├── 事件监听在 onLoad 中注册
    ├── 事件在 start 之前就被触发
    └── 处理函数中访问了 start 中初始化的变量
```

### Playable 广告常见故障树模式

```
某渠道白屏 (OR):
├── SDK 未就绪 (AND):
│   ├── mraid.getState() !== 'ready'
│   └── 代码未等待 ready 事件
├── 资源加载失败 (AND):
│   ├── base64 内联不完整（打包工具截断）
│   └── 无 fallback 处理
├── 容器尺寸为 0 (AND):
│   ├── 渠道容器初始化延迟
│   └── Canvas resize 未监听
└── CSP 策略限制 (AND):
    ├── 渠道 iframe 有严格 CSP
    └── 代码使用了 eval / inline style
```
