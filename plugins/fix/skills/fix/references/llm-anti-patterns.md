# LLM 反模式防护清单

## 概述

专门针对 AI 助手在调试中的特有坏习惯设计的防护机制。在 Phase 1（根因调查）和 Phase 3（假设验证）中执行自检。

## 反模式清单

| 反模式 | 表现 | 检测方法 | 强制行动 |
|--------|------|----------|----------|
| **幻觉 API** | 声称某方法/参数存在但未验证 | 检查是否在代码库中 grep 过该 API | grep 确认 + 查阅官方文档 |
| **虚假记忆修复** | 凭训练数据经验提出方案而非基于当前代码 | 检查是否引用了当前文件的具体行号 | 必须引用当前文件具体行号 |
| **过度泛化** | 套用相似但不完全匹配的解决方案 | 检查是否列出了当前场景与参考方案的差异 | 必须列出差异点 |
| **信心校准失败** | 对猜测使用确定性语言 | 检查是否使用了三级标注 | 强制使用三级标注 |
| **症状修复** | 在报错处加 try-catch / 忽略错误 / 绕过检查 | 检查修复位置是否在报错处而非源头 | 追踪到源头再修 |
| **堆叠修复** | 一次改多处或在失败修复上叠加新修改 | 检查本次是否修改了多个不相关的位置 | 一次只改一处 |
| **循环变体** | 对同一思路的微调连续尝试 2 次以上 | 检查连续两次修复是否属于同一类型 | 强制换完全不同的角度 |

## 信心三级标注

每个结论和假设**必须**标注信心等级：

### [已验证]
- **含义**：通过代码搜索、运行测试、或文档确认
- **允许行动**：可以基于此结论行动和修改代码
- **示例**："Sprite 组件在 3.x 中没有 width 属性 [已验证] — 查阅官方 API 文档确认"

### [高度怀疑]
- **含义**：有间接证据但未完全确认
- **允许行动**：先写诊断代码验证，验证后升级为 [已验证]
- **示例**："git blame 显示 commit abc 改了这行，可能引入了问题 [高度怀疑] — 需要对比前后版本确认"

### [假设]
- **含义**：仅基于推理，无直接证据
- **允许行动**：**禁止直接修复**，必须先收集证据将其升级或排除
- **示例**："可能是异步加载时序问题 [假设] — 需要添加日志确认执行顺序"

## 显式不确定性协议

### 当不确定时必须：

1. 明确说 **"我不确定 X，需要验证"**
2. 列出具体的验证步骤
3. **执行验证后**再继续

### 禁止使用的表述（无验证时）：

| 禁止表述 | 问题 | 应替换为 |
|----------|------|----------|
| "这应该能工作" | 无验证的确定性 | "根据 [证据]，这应该能工作 [已验证]" |
| "试试这个" | 无假设的盲试 | "假设根因是 X [高度怀疑]，验证方法是..." |
| "可能是因为..." | 无证据的猜测 | "我怀疑是 X [假设]，需要通过 Y 验证" |
| "一般来说..." | 依赖训练数据而非当前代码 | "在当前代码库中，grep 发现..." |
| "通常这样做..." | 依赖通用经验 | "对比 [同项目可工作代码]，差异在于..." |

## 自检清单

在 Phase 1 和 Phase 3 中执行以下自检：

- [ ] 我引用的每个 API/方法是否都在代码库中 grep 确认过存在？
- [ ] 我的每个结论是否都标注了信心等级？
- [ ] 我是否在修复症状而非根因？（修复位置是报错处还是源头？）
- [ ] 我是否在一次修改中改了多个不相关的地方？
- [ ] 我是否在使用确定性语言描述未验证的假设？
- [ ] 我连续两次的修复是否属于同一思路的变体？

**任何一项为 YES → 停下来，返回 Phase 0 重新收集证据。**
